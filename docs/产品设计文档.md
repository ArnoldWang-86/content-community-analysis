# 数据分析工具 · 产品设计文档

> 项目：Text-to-SQL 数据 Agent（自然语言问数系统）
> 形态：内部数据分析工具
> 时间：2026.09 – 至今
> 说明：这是一份按产品文档格式整理的记录，用于说明这个工具**为什么这样做**，而不只是**做了什么**。

---

## 一、需求背景

### 问题

在数据驱动的工作方式里，取数是最高频也最消耗人力的环节。**业务方不会写 SQL，分析师大量的时间花在重复取数上。**

具体表现为三个断点：

| 环节 | 现状 |
|---|---|
| 提需求 | 业务方说不清要什么，只能描述"我想看看最近哪个品类卖得好" |
| 排期 | 需求进队列，简单取数也要等 |
| 交付 | 交出去的是一张表或一张图，业务方还要再问"所以呢？" |

### 目标用户

**非技术背景的业务 / 运营人员。** 他们的共同特征是：

- 有明确的业务问题
- 能读懂数据和图表
- 但不会写 SQL，也不了解库表结构

### 产品目标

让业务人员**用自然语言提问，直接得到数据结论**——不需要写 SQL，也不需要理解表结构。

---

## 二、需求优先级

按 MoSCoW 拆分：

| 优先级 | 需求 | 理由 |
|---|---|---|
| **Must** | 自然语言输入 → 返回数据结果 | 这是产品存在的理由 |
| **Must** | 只允许查询，禁止任何写操作 | 一旦放开写权限，一次模型幻觉就可能破坏数据 |
| **Must** | 结果必须带业务解读 | 只给一张表，业务方还是要来问"所以呢"，没解决根本问题 |
| **Should** | 自动生成图表 | 降低理解成本，但不是阻塞项 |
| **Should** | 模型写错时能自动修复 | 模型首次写错是常态，不自愈的话可用性很低 |
| **Won't（v1 不做）** | 多轮对话 | 会显著增加复杂度，先用单轮验证核心链路 |

---

## 三、方案设计

### 整体链路（七个环节）

```
语义层检索 → SQL 生成 → 安全校验 → 执行 → 错误自愈 → 结果解读 → 自动出图
```

### 各环节的职责划分

这个设计里最重要的一条原则是：**模型负责理解，代码负责确定的事。**

| 环节 | 由谁做 | 为什么 |
|---|---|---|
| 语义层检索 | 代码 | 库表结构和业务口径是确定的知识，不需要模型推理 |
| SQL 生成 | **模型** | 「把业务问题翻译成查询」是理解任务，只有模型能做 |
| 安全校验 | 代码 | 安全是确定性问题，必须用规则而不是模型判断 |
| 执行 | 代码 | — |
| 错误自愈 | 模型 + 代码 | 模型负责改写，代码负责控制重试上限 |
| 结果解读 | **模型** | 「这组数据说明什么」是理解任务 |
| 自动出图 | 代码（类型）+ 模型（指标列） | 图表类型是确定性规则；「该看哪一列」需要理解语义 |

## 四、关键取舍与决策记录

### 决策 1：为什么不让模型生成的 SQL 直接执行

**这是整个产品最重要的一条决策。**

```
模型生成的 SQL 语法完全正确，但它可能：
  · 写成 DELETE / UPDATE（模型被 prompt injection 诱导）
  · 堆叠多条语句（SELECT 1; DROP TABLE）
  · 语法正确但语义错误（把小样本当成结论）

如果直接把模型的输出丢给数据库执行，
上面任何一种情况都会造成真实损失。
```

**方案**：在生成和执行之间加一道**安全闸门**。

- 只放行单条 SELECT
- 拦截全部写操作关键字、堆叠语句、大小写变体
- 校验失败直接中断，不执行

**这个设计的本质是：模型输出不可控，但「执行什么」必须由代码决定。**

### 决策 2：为什么把业务口径做成语义层，而不是写进 Prompt

因为口径需要**被复用、被版本管理、被单独维护**。

塞进 Prompt 里的问题是：每次改口径都要动 Prompt，Prompt 会越来越长越来越乱，而且改了什么无从追溯。

做成独立的语义层之后：

- 口径说明与库表结构解耦，可以单独更新
- 同一份口径可以被多个 Prompt 复用
- 新增字段或新增陷阱时，只改一处

**实际收益**：这个设计后来帮我发现并修复了一类「语义幻觉」——模型生成的 SQL 语法完全正确、也能跑出结果，**但结论是错的**（它没过滤小样本，把一个只有 3 条数据的分区选成了"互动率最高"）。修正方式就是在语义层里补充统计可靠性规则。

### 决策 3：为什么图表类型用规则，而不用模型

图表类型是一个**确定性问题**：有序维度用折线、类别少且单指标用饼图、其余用柱状图。

让模型决定图表类型会带来两个问题：一是多一次 API 调用（成本和延迟）；二是同一个问题问两次可能画出不同的图，**不确定性对工具类产品是减分项**。

**所以这一环节用规则。**

### 决策 4：但「该看哪一列」必须交给模型

这是上一个决策的另一面。

```
图表规则只能决定"画什么形状"，
但决定不了"该用哪一列做 Y 轴" ——

因为「用户问的是互动率还是播放量」是语义问题。
```

我在开发过程中踩过这个坑：自动出图上线后，画「粉丝量级与互动率的关系」，**结果画出来的是"各档位有多少个视频"**——因为代码取了结果集的第一列，而第一列恰好是样本量。

修完之后还是错的，**再查才发现根因在更底层**：MySQL 的 `ROUND(AVG(x), 4)` 返回 DECIMAL 类型，经过驱动映射后 pandas 把它存成了 object（字符串）类型，导致"哪些列是数值列"的判断失效。

**最终方案**：在生成 SQL 的环节，让模型**顺便指定**该用哪一列做图表 Y 轴，写进结构化输出的 `metric` 字段。

**这条决策的启示**：不是所有环节都该由模型或代码单方面决定。**「用户想看什么」是语义判断，代码做不了；「怎么把图画对」是确定性问题，不该交给模型。**

### 决策 5：错误自愈的重试上限为什么是 3 次

| 次数 | 考虑 |
|---|---|
| 1 次 | 太激进，很多错误需要结合报错信息才能修对 |
| 3 次 | 实测能覆盖绝大多数可修复错误（字段名幻觉、表名幻觉、语法错误） |
| 5 次以上 | 边际收益低，且可能陷入"改坏 → 再改坏"的循环 |

**同时做了一个判断**：如果报错是**连接层错误**（比如数据库没启动），不应该重试——那不是 SQL 的问题。这一点在实测中验证过：当时数据库没启动，自愈逻辑正确识别出"错误不在 SQL 本身"，没有盲目改写语句。

## 五、衡量指标

**这个工具好不好用，我用四个指标衡量：**

| 指标 | 含义 | 实测 |
|---|---|---|
| **首次生成可用率** | 模型第一次生成就能执行的 SQL 占比 | 4 类业务问题均可跑通 |
| **自愈成功率** | 报错后能自动修复并成功执行的比例 | 故障注入 3 类故障 **3/3 修复成功** |
| **单次问数耗时** | 从一个问题到拿到结论的时间 | **4–7 秒**（含 2 次模型调用） |
| **测试通过率** | 自动化测试的通过比例 | **61 passed / 2 xfailed** |

**其中"自愈成功率"是最关键的指标。** 因为它的验证方式比较特殊——**简单问题上模型一次就写对，自愈逻辑永远不会被触发，也就无法验证它到底有没有用。**

所以我写了一个**故障注入器**，主动把正确的 SQL 改坏（字段名幻觉、表名幻觉、语法错误），再看自愈逻辑能不能修回来。

**这个做法在测试领域叫故障注入，本质上是「测试容错逻辑本身是否可靠」。**

## 六、迭代记录

| 版本 | 变更 | 触发原因 |
|---|---|---|
| **v1.0** | 基础链路跑通（生成 → 校验 → 执行 → 解读） | 初始版本 |
| **v1.1** | 补充语义层约束规则 | 发现「语义幻觉」：SQL 语法正确但选出了只有 3 条数据的分区 |
| **v1.2** | 自动出图改为由模型指定指标列 | 发现图表画错指标（画成了样本量） |
| **v1.3** | 在数据读取层做类型规范化 | 定位到 DECIMAL → object 的类型问题 |
| **v1.4** | 补充故障注入与 pytest 测试套件 | 自愈逻辑无法被自然触发，需要主动制造失败来验证 |

**每一次迭代都不是"我想加个功能"，而是"用的时候发现了问题"。**

## 七、局限与未做的事

**第一，没有多轮对话。** 用户不能追问"那第二名的呢"——每次提问都是独立的。做多轮需要维护会话上下文，会显著增加复杂度，v1 阶段用单轮验证核心链路更划算。

**第二，语义层依赖人工维护。** 新增字段或新增业务口径时，需要人工更新语义层。**没有做自动同步**——因为口径本来就是人的判断，不是能从表结构里推出来的。

**第三，只在一份数据集上验证过。** 我是在自己的项目数据（19,456 条记录、4 张表）上做的验证。**换一套完全不同的库表结构，需要重新配置语义层**，通用性还没有验证过。

**第四，安全校验有一处已知误报。** 当前用正则匹配危险关键字，无法区分"代码里的关键字"和"字符串字面量里的关键字"——所以 `SELECT 'drop' AS word` 这样的合法查询会被误拦。我没有隐瞒这个问题，而是用 `xfail` 把它记在测试里，并写明改进方向（先剥离字符串字面量和注释，或改用 SQL 解析器做语法树级校验）。

## 八、复盘

**这个项目里我最大的收获，是理解了"模型与代码的分工边界"。**

不是所有环节都该交给模型，也不是所有环节都该用规则写死。判断标准其实很清楚：

- **需要理解语义的**（用户问的是什么、这组数据说明什么）→ 交给模型
- **确定性的**（安全、类型、图表规则、重试上限）→ 写成代码

**而最容易出问题的地方，恰恰是两者的交界处。**

比如「自动出图」这个环节：图表类型是确定性的（该用规则），但"该画哪个指标"是语义的（该用模型）。我一开始把两者都交给了规则，结果图画错了指标；**修的时候又一度想把两者都交给模型，但那样会引入不必要的不确定性。**

**最后的分工是：规则决定形状，模型决定看哪一列。**
